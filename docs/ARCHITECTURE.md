# BuildScope AI — Architecture

## Purpose

BuildScope AI is a single-tenant demonstration of a **Construction Sales & Automation Platform**. It preserves the production-shaping rules of the master prompt: estimates and scores are deterministic, AI augments rather than blocks lead capture, and every CRM data access resolves the company tenant on the server.

## Implementation map

| Concern | Implementation |
|---|---|
| Public site and calculator | React 19, Vite, TypeScript, Tailwind CSS |
| CRM API | Express + tRPC procedures |
| Persistence | Drizzle ORM on the managed MySQL/TiDB service |
| Company scoping | `companyId` is a required FK on CRM and automation records; server obtains it from the configured demo company rather than client input |
| Estimate engine | `server/buildscope/business.ts`, pure deterministic functions |
| AI qualification | `server/buildscope/qualification.ts`, server-only structured output with a Zod validation gate and rule-based fallback |
| PDF | On-demand deterministic portable PDF payload generated by `server/buildscope/proposal.ts` |
| Notifications and follow-ups | Persisted queue records visible in CRM; customer sending stays approval-gated |

## Non-negotiable business logic

`estimateProject()` is the only source of financial output. The result is always an interval rounded to the nearest 0.5 or 1.0 million KZT, based on its size. `scoreLead()` consumes confirmed structured data and the optional AI intent signal, but final score calculation is deterministic and explainable.

## AI safety and graceful degradation

Free-text notes are wrapped as untrusted input. The system prompt forbids the model from executing note-borne instructions and from producing prices or score values. Responses must match a strict JSON schema and a Zod schema. If the provider, output, or parsing fails, the lead is still created with a rule-based summary and `needsManualReview = true`.

## Demo assumptions

The requested architecture named Next.js, FastAPI, PostgreSQL, WeasyPrint, and Railway. This WebDev delivery uses the supplied React/Express/tRPC/MySQL runtime to provide the same business behavior in one deployable managed project. The database remains relational, all tenant boundaries are modeled, and all client writes go through server procedures.

Telegram is represented by a persisted **Telegram outbox** record because no bot token/chat ID was supplied. In production, a server-side integration adapter should send that outbox entry using credentials stored as platform secrets. Customer follow-ups are deliberately created as `pending` drafts; no customer message is automatically sent. The downloadable proposal is generated on demand. A production version should persist its binary into object storage and retain a time-limited signed URL.

The showcase CRM deliberately renders its seeded tenant in a demonstration mode so that the 3–5 minute sales scenario can run without a user account. The schema includes CRM roles and the server resolves the tenant internally. Before any production launch, activate `protectedProcedure` for CRM mutations and use the signed-in user’s server-side company and CRM role to enforce owner/manager/analyst permissions; do not accept a tenant identifier from the browser.

## Background processing

A production follow-up scheduler must be a platform-managed HTTP Heartbeat callback, not an in-process timer. It should be deployed before scheduling, mounted at `/api/scheduled/*`, be idempotent, and lookup work by the platform task UID. No schedule is activated in this demo because deployment and a final user decision on timing are prerequisites.
